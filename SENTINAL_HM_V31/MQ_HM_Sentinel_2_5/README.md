# HM 2.5 — keep centering during the shot

Minor update from HM 2.4. Separate the fine-centering target from laser permission. The requested target remains zero angle error; entering a laser acceptance window does not finish centering.

## Change

HM 2.4's `centred()` predicate suppressed new fine pulses whenever the laser entry angle/rate/IR/wheel conditions passed. That meant an error between 0.18 and 0.90 degree could qualify for laser operation yet rely solely on the gentler hold controller.

HM 2.5 removes that coupling. In both FINE and FIRE:

- Beyond +/-0.18 degree, the existing short fine pulses remain eligible, even inside the laser entry window. Existing rate inhibition, pulse amplitude, 5-20 ms duration and minimum 180 ms inter-pulse settling remain.
- A pulse stops at target crossing, at or inside +/-0.18 degree, at its duration limit, or at the existing rate limit.
- Inside +/-0.18 degree, pulses stop but `fineHoldPWM()` still uses the full signed angle error and measured rate, plus learned load bias. This band is a pulse threshold, not a zero-output deadband. It continues trying to restore zero error and counter drift, within sensor and PWM resolution.
- The actual `motorUpdate()` dispatcher continues calling fine control every nominal 5 ms in FIRE as well as FINE. Laser permission does not freeze the motor command.

HM 2.4 firing limits are retained: entry +/-0.90 degree, existing hold hysteresis out to +/-1.30 degrees, existing motion/IR/wheel checks and bounded-centred-ripple handling. Zero remains the aim point throughout. Two-second firing duration, controlled departure afterward, two-second startup and V35 coarse/search control are retained. More fine corrections may increase visible jitter or interrupt a shot if motion limits are exceeded; physical testing is required to assess the trade-off.

## EEPROM and validation

Same format-23 EEPROM implementation and 1,019/1,024-byte allocation as [HM 2.4](../MQ_HM_Sentinel_2_4/README.md). Startup/dump labels now identify HM 2.5. Preserved format-23 records may have been generated by an earlier release; label and save them before another armed run. The decoder accepts HM 2.3, 2.4 and 2.5 dumps. Speed-guard event filtering, CRC/commit checking, direct measurements, rolling samples and retained-event allocation remain.

Nano ATmega328P old bootloader compile: **29,262/30,720 flash bytes**, 810/2,048 static RAM bytes. Not uploaded or physically tested during this update.

`validate_centering.py` extracts the actual fine controller, hold function, motor dispatcher, fire tolerance and entry predicate. With hardware stubs it checks that laser-qualified +/-0.5 and +0.85 degree errors still trigger appropriately signed motor pulses in both FINE and FIRE, reaching the inner tolerance ends a pulse, motion inside the pulse tolerance still receives damping, and pulse timing/rate inhibition remain. It compares the HM 2.4 firing/hold/departure functions and constants plus EEPROM implementation (apart from version strings).

`validate.py` retains the signed codec, full PWM range, CRC, interrupted-write, storage/queue, reboot, dump-order, centred-ripple and two-second departure checks. The tests do not model motor/string dynamics or establish physical bullseye accuracy.

From repository root:

```
python3 SENTINAL_HM_V31/MQ_HM_Sentinel_2_5/validate_centering.py SENTINAL_HM_V31/MQ_HM_Sentinel_2_4/MQ_HM_Sentinel_2_4.ino
python3 SENTINAL_HM_V31/MQ_HM_Sentinel_2_5/validate.py MQ_Sentinel_V35/MQ_Sentinel_V35.ino
arduino-cli compile --fqbn arduino:avr:nano:cpu=atmega328old SENTINAL_HM_V31/MQ_HM_Sentinel_2_5
```
